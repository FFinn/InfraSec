# Приложение InfraSec

Один образ запускает два отдельных сервиса. Веб-приложение проверяет вход через Keycloak и обращается к внутреннему сервису. Внутренний сервис принимает запросы только с правильным API-ключом.

## Запуск

Контекст сборки — каталог `app`:

```bash
docker build -t infrasec-app app
```

Команда веб-приложения:

```bash
uvicorn infrasec.web:create_app --factory --host 0.0.0.0 --port 8000 --no-access-log
```

Команда внутреннего сервиса:

```bash
uvicorn infrasec.backend:create_app --factory --host 0.0.0.0 --port 8000 --no-access-log
```

Образ запускается с UID/GID 1000. Python не создаёт файлы байт-кода, поэтому приложение может работать с корневой файловой системой только для чтения. Файл Vault Agent должен быть доступен UID 1000.

## Конфигурация

`VAULT_CONFIG_FILE` указывает на JSON-файл, подготовленный Vault Agent; по умолчанию `/vault/secrets/config.json`.

| Сервис | Обязательные поля JSON |
|---|---|
| Веб-приложение | `oidc_client_secret`, `session_secret`, `backend_api_key` |
| Внутренний сервис | `api_key` |

Значение `backend_api_key` должно совпадать с `api_key` внутреннего сервиса. Ключ подписи сеанса `session_secret` должен содержать не менее 32 символов. Значения создаются и хранятся в Vault; в образ они не включаются.

| Переменная веб-приложения | Назначение |
|---|---|
| `KEYCLOAK_PUBLIC_URL` | Публичный адрес realm для браузера и проверки `issuer` |
| `KEYCLOAK_INTERNAL_URL` | Адрес того же realm для обмена кода на токены и получения JWKS |
| `OIDC_CLIENT_ID` | Идентификатор клиента; по умолчанию `infrasec-web` |
| `APP_PUBLIC_URL` | Адрес приложения в браузере; callback — `<адрес>/auth/callback` |
| `BACKEND_URL` | Адрес внутреннего сервиса; по умолчанию `http://backend:8000` |
| `SSL_CERT_FILE` | Открытый сертификат CA для проверки TLS Keycloak |
| `KEYCLOAK_CA_FILE` | При необходимости отдельный CA Keycloak, имеет приоритет перед `SSL_CERT_FILE` |

Разные публичный и внутренний адреса нужны для подключения через SSH: браузер открывает локальный проброс порта, приложение на ВМ обращается к Keycloak по внутренней сети. Ожидаемый `issuer` остаётся публичным адресом realm. Проверка TLS не отключается.

## Проверка работы

- `/health` у обоих сервисов сообщает готовность и наличие корректного файла конфигурации без показа значений.
- `/login` начинает вход OIDC Authorization Code с PKCE S256.
- `/auth/callback` проверяет подпись ID token, issuer, audience, nonce и state средствами Authlib.
- `/profile` после входа показывает имя пользователя LDAP и проверяет обращение к внутреннему сервису. Эта страница подходит для демонстрации всей цепочки.
- `/api/data` делает ту же проверку и возвращает JSON без секретов.
- `POST /logout` завершает сеанс приложения.
- Внутренний `/data` требует заголовок `X-API-Key`; сравнение выполняется через `hmac.compare_digest`.

В cookie хранятся только сведения пользователя и временное состояние процедуры входа. ID/access/refresh token туда не записываются. Cookie подписана, имеет `HttpOnly`, `SameSite=Lax` и срок 15 минут. Для адреса приложения с HTTPS автоматически включается `Secure`. Локальный HTTP допустим только для описанного подключения через SSH.

Файл секретов перечитывается при запросах. После замены ключа сеанса старые cookie перестают приниматься. Приложение и внутренний сервис получают заменённый API-ключ без перезапуска. Журнал HTTP-запросов Uvicorn отключён, чтобы callback с кодом OIDC не попадал в лог.

## Тесты

Из корня репозитория:

```bash
python3 -m venv app/.venv
app/.venv/bin/python -m pip install -r app/requirements-dev.txt
app/.venv/bin/python -m pytest -p no:cacheprovider -q tests/test_app.py
```

Тесты выполняют настоящий обмен Authlib с тестовым OIDC-сервером в памяти и проверяют подписанный RS256 ID token. Проверяются также неверные issuer/audience/nonce/state/подпись, запрет доступа без входа, подделка cookie, замена ключей, экранирование имени пользователя и отсутствие секретов в HTTP-ответах. Это дополняет проверку с работающими Keycloak и LDAP, но не заменяет её.
